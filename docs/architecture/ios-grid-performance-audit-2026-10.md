### 1. P1：收藏快照逐部查询并装载完整章节

定位：`SourceLibrary.kt:31,39,370`、`IosLibrary.kt:217`、`LibraryModel.swift:109`。

`snapshot()` 调用 `favourites()` 后，逐部调用默认 `withChapters=true` 的 `content()`，
每部执行一次 `getChaptersDao().findAll(id)`。即使没有任何章节，6000 部仍有 6000 次章节查询；
有章节时还会构建所有 `SourceChapter`。作品库空间过滤在这之后才发生。
`history()` 同样装载完整章节，此外还单独查询正在阅读的章节。

| 合成收藏数 | 每部章节数 | 收藏读取 | 实际装载章节 |
|---|---:|---:|---:|
| 100 | 0 | 42.0 ms | 0 |
| 1000 | 0 | 450.4 ms | 0 |
| 6000 | 0 | 2790.3 ms | 0 |
| 6000 | 20 | 7482.4 ms | 120000 |

这些是异步 API 总延迟，不是同等时长的主线程阻塞。10 ms 主队列定时器在热态 API 期间最大间隔
大多为 11–17 ms；120000 章节的首轮收藏读取出现一次 71.7 ms 最大间隔。
该探针不是帧率或 hitch 检测，不能据此证明界面无掉帧或归因这次间隔。

建议：为集合页提供轻量快照，批量读取列表必要字段、进度与章节数量，完整章节留给详情/阅读入口；
继续阅读所需的最近章节标题和恢复位置仍须保留。不能简单移除章节而不核对消费者。
同时合并启动与视图出现时的重复 refresh；现有索引只消除了视图内过滤，尚未消除全库重读。

### 2. P1：没有新章节时，更新读取仍逐条查询所有跟踪记录

定位：`IosLibrary.kt:307`、`TracksDao.kt:24`。

`updates()` 先 `findAllIds()`，再对每个 ID 调用 `find(id)`，之后才判断 `newChapters > 0`。
6000 条零更新记录仍需 6001 次显式 DAO 查询；有更新还会继续查询作品及完整章节。

| 跟踪数，全部零更新 | 热态读取耗时 |
|---|---:|
| 100 | 24.5 ms |
| 1000 | 248.5 ms |
| 6000 | 1569.4 ms |

该路径由每次 `refreshRecords()` 执行，不限于用户打开更新页。
建议直接查询有更新的跟踪记录，再用已有批量作品读取能力构建列表；保持更新时间排序。
即使暂不新增 DAO，已有批量接口也值得优先于逐条查找评估。

### 3. P1：缺失来源检查重复读取同一份收藏、历史和章节

定位：`ContentView.swift:115`、`IosLibraryRecovery.kt:50`。

`recordsRevision` 更新后触发来源检查，但检查没有复用刚发布的收藏/历史，
而是再次调用 `library.favourites()` 和 `library.history()`，完整重建 DTO。
最终聚合实际只使用来源、作品 ID 和收藏/历史标志。

| 收藏数 | 每部章节数 | 缺失来源检查热态耗时 |
|---|---:|---:|
| 100 | 0 | 84.7 ms |
| 1000 | 0 | 530.4 ms |
| 6000 | 0 | 3086.4 ms |
| 6000 | 20 | 7831.1 ms |

所以“来源缺失提示是否相关”需要区分：`MissingSourcesNotice` 的绘制只遍历缺失来源数组；
其数据检查确有全库重读成本。没有观察到它在每个滚动帧重新执行。
建议在数据层查询轻量的来源引用并聚合，保留有效分类、软删除、身份去重语义；
或复用有明确版本边界的快照，来源安装状态变化时重新聚合，不必重新装载章节。

### 4. P1（下载时）：每页进度在主 actor 编码并原子写入完整队列

定位：`ReaderDownloadQueue.swift:192,221`、`ContentCollection.swift:184`。

探针让真实队列执行 14 次页进度回调，舍弃前两次计时；每种规模重复两轮。其余任务处于暂停状态，
只有一项执行，避免网络、并发下载和后台扫描干扰。

| 队列 | JSON 大小 | 单次进度平均耗时，两轮 |
|---|---:|---:|
| 1 项，payload 1 KiB/项 | 1.2 KB | 0.47 / 0.45 ms |
| 100 项，payload 1 KiB/项 | 119 KB | 1.57 / 1.47 ms |
| 500 项，payload 1 KiB/项 | 597 KB | 5.34 / 5.34 ms |
| 500 项，payload 8 KiB/项 | 4.18 MB | 22.98 / 21.27 ms |

最大单次 28.4 ms。生产方法被 `@MainActor` 隔离；这些同步序列化/写盘成本会直接占用界面执行时间。
每轮 14 次进度连同开始/完成共发布 16 次 entries，使用整个队列环境对象的集合视图也会被通知。
没有下载任务时，这条路径不能解释持续卡顿。

建议将进度展示与持久化频率分离，串行后台保存有界快照；暂停、完成、退出和存储维护时必须保证
检查点与错误处理语义，不能仅将写盘改为无序的 fire-and-forget。

### 5. P2：历史/来源集合反复构建全库收藏角标

定位：`ContentCollection.swift:191,220`、`LibraryRecordsView.swift:181`。

在 6000 部真实 Kotlin DTO、每组显示 9 项、无更新/下载条目的隔离输入上，原样 `marked()`：

| 设置 | 1 组平均 | 5 组平均 |
|---|---:|---:|
| `marksFavourites=false`（作品库） | 0.017 ms | 0.084 ms |
| `marksFavourites=true`（来源/历史等） | 9.91 ms | 49.14 ms |

全局收藏 Set 在每个集合 body 求值时重建；历史按日期生成多个集合会重复支付。
**作品库本身已经关闭收藏角标，这个扫描不能用来解释当前作品库的视频网格。**
建议在收藏快照边界共享身份 Set，更新/下载完成集合也以各自的实际状态变化为失效边界；
不因每页下载进度而重建不变的收藏身份。真实 body 调用频率仍需 UI 采样验证。

## 重要更正：全库 6000 多部，视频空间仅 9 部

用户进一步澄清：全库收藏 6000 多部，视频空间过滤后只有 9 部，且保留了很多空分类。
这与此前假定的“小作品库”不同，重新提高了全量数据派生的排查优先级。

### 已确认的重复扫描

`LibraryView.swift` 的调用关系为：

```text
categoryBar.ForEach(visibleCategories)
  → count(category.id)
    → kindFavourites
      → availableKinds：扫描全部收藏并桥接 mediaKind
      → filter：再次扫描全部收藏，仅保留视频
    → 过滤视频结果，计算当前分类数量
```

`availableKinds` 作为 `ContentSpace.filter` 的实参，会先求值；即使已启用全局视频空间、函数直接返回
`space`，仍会先扫描全库。每个分类又重新调用一次上述路径。因此一次分类栏求值的扫描开销近似
`O(分类数 × 全库收藏数)`，不能按最终可见的 9 部估算。

空分类仍显示，是因为 `visibleCategories` 仅检查 `isVisibleInLibrary`，不检查当前空间的分类数量。
它会增加分类视图数，并放大上述重复扫描；隐藏空分类与缓存派生数据是两个不同的处理点。

### 临时探针与结果

在当前源码上构建临时诊断包，记录 `availableKinds` / `kindFavourites` 的调用次数和主线程耗时。
为避免改动数据库，用原有 Kotlin DTO 在内存中生成测试读模型：重复非视频条目作为 5991 个其他媒体
记录，保留 9 个不同来源/身份的视频条目，共 6000 条。模拟器约 70 个可见分类。
视频网格可见身份唯一；非视频重复项不在当前空间中显示。

它验证实际 SwiftUI → Kotlin DTO 过滤路径，不是用户真实的 6000 部数据；共享 DTO 的缓存局部性、
分类分布、设备、系统和构建均可能改变耗时，不能将这些数字当作真机测量。

- 诊断构建通过；日志为 `filter-audit-build.log`、`filter-audit-build-2.log`。
- 在 6000/9 场景的初始化与状态更新期间，`kindFavourites` 累计记录约 1900 次，累计约
  **20,535 ms**；`availableKinds` 累计约 **11,748 ms**。
- 后者包含在前者内，不能相加。累计耗时包含多次初始状态更新，不是“单次过滤耗时 20 秒”。
- 页面稳定后记录时间点并操作多次上下滑动，50 次粒度的计数没有继续增长；一次分类栏求值会经过
  约 70 个分类，因此本轮没有观察到纯滚动触发整组分类重算。
- **已确认更新时重复扫描；尚未确认用户系统上每帧滚动都会过滤。** 这次测试也不能排除用户系统
  在滚动/顶底栏变化时产生更多视图更新。

本轮开始准备了提示条显示/隐藏/移除的临时开关；收到全库规模信息后优先测量过滤。
提示条三组对照尚未形成有效结论，不能声称已排除或确认它。

修复方向应优先将媒体类型集合、空间过滤结果与分类计数，按收藏快照及空间选择变化生成并复用，
使每个分类查询预先生成的计数字典。无需在每个分类里重新过滤 6000 条。
单纯在 `body` 中缓存一次局部数组可以减少分类间重复，但若父视图频繁更新，仍会再次过滤全库；

## 用户补充：列表流畅，网格卡顿

该对照改变排查优先级。两种作品显示模式都经过 `ContentCollection.marked`、`CoverFrame`、
`CoverImage` 和同一解码缓存，网络/JNI、后台缓存维护、下载队列持久化也没有按显示模式分支。
因此下列通用缺陷不能单独解释“仅网格卡顿”，只能作为可能被网格放大的成本。
P1/P2 表示实现问题的处理优先级，不表示已经确认它对本次卡顿的贡献。

网格与普通列表的直接差异：

| 差异 | 网格 | 普通列表 | 下一步验证 |
|---|---|---|---|
| 容器 | 自适应列 `LazyVGrid` | `LazyVStack` | 比较热缓存下布局/视图更新时间 |
| 封面显示 | 默认目标宽 96 pt，按列分配实际宽度 | 固定宽 48 pt | 相同内容和缓存下比较渲染轨道 |
| 封面附加内容 | 进度、收藏/下载/成人标记 | 关闭 `showsProgress` 和 `showsMarks` | 逐项关闭效果测量，不提前归因 GPU |
| 摘要 | `GridCard.body` 内调用 `ContentText.firstLine` | 普通列表不处理摘要 | 检查长 body 是否落在正则/字符串处理 |
| 紧凑网格 | 额外渐变、文字阴影、局部圆角裁剪 | 无此覆盖层 | 普通网格与紧凑网格分别对比 |

定位：`ContentCollection.swift:190,202,280,284,298,323,423`。
固定海报比例下，96 pt 相对 48 pt 的单张显示面积是 4 倍；实际列宽、同屏数量及渲染成本仍需测量。
两种模式都已有封面阴影，不能把“列表没有阴影”当作解释。
普通网格摘要清洗位于视图求值路径，执行两次正则替换；`.lineLimit(1)` 只限制显示，
不会限制先前字符串处理的长度。它不适用于没有摘要/已有 subtitle 的作品，也不适用于紧凑网格。

优先对照顺序：同一已加载内容的列表/网格 → 网格效果开关 → 摘要预处理 → 封面尺寸档位。
如果热缓存仍卡顿，先看布局/渲染和 body；只有新图进入时卡顿，再查解码/图片交付链路。
目前这是一组待验证的诊断分支，尚无可重复捕获用户原始卡顿的自动化闭环。

## 发现

### 1. P1：扩展源网格封面使用阅读器解码规格，明显降低缓存容纳量

- `iosApp/Kototoro/SourceBrowseView.swift:512`：扩展/本地源封面通过 `artifact.decodedImage()` 解码；
  普通 URL 封面通过 `CoverCache.decode`，其长边限制为 600。
- `iosApp/Kototoro/SourceImageLoader.swift:199`：`decodedImage` 调用 `loadedPage`，最终进入
  `ReaderImageArtifact.load`；第 54–61 行读取、校验、取得尺寸并按 `IosReader.decodeSize` 解码。
- `ios-shared/.../IosReader.kt:235` 与第 394 行：阅读器预算为 4,194,304 像素、最大单边 16,384，
  并非网格缩略图预算。1200×1800 图片会保留原尺寸。
- `ios-shared/.../IosSources.kt:682`：所有该路径封面都请求 `fetchCover(content.value, true)`，
  包括小网格；Parser/Mihon/Aniyomi 宿主会优先选 `largeCoverUrl`。
- `iosApp/Kototoro/SourceBrowseView.swift:572`：共享解码缓存成本上限为 64 MiB。

影响条件：源提供较大封面、浏览条目多、往返滑动且对应视图图片状态已释放。大位图会更早触发缓存
淘汰，重新进入时又经历宿主文件获取、校验和解码；同时增加渲染资源压力。
`NSCache` 上限不是严格驻留保证，视图的 `@State image` 还可能额外持有图片；不能把成本上限当作总内存上限。

建议：保留源客户端及请求头链路，分离封面与阅读器解码策略；按用途和显示像素设定有限的尺寸档位，
使网格、附件、详情大图使用匹配规格，并让缓存键包含尺寸档位。避免把整个详情封面也固定降为 600。
采用单一封面加载入口复用请求与校验，符合 DRY；只分离当前确有差异的解码职责，符合 SRP/KISS。

### 2. P1（下载进行中）：每页进度在主线程序列化并原子重写整个队列

- `iosApp/Kototoro/ReaderDownloadQueue.swift:51`：整个队列类是 `@MainActor`。
- 第 216–221 行：下载进度回调进入 `update`。
- 第 185–200 行：复制条目数组，编码完整 `Snapshot`，创建目录，执行同步 `Data.write(.atomic)`，
  然后发布 `entries`；队列允许最多 500 项、32 MiB 编码数据。

影响条件：一边下载一边滚动，尤其队列较大或本地下载连续快速完成页面时。
这些同步工作直接占用 UI 执行时间；这是代码可确认的阻塞路径，但本次未测量用户队列的耗时。
没有下载时，此项不能解释持续卡顿。

建议：将编码/持久化放到串行后台存储边界，保持写入顺序、失败回滚、重启检查点与维护互斥语义；
UI 进度发布和持久化频率分别设计，不能简单异步抛出后就宣称保存成功。

### 3. P2：共用网格观察整个下载/作品库对象，更新时全量重建角标

- `iosApp/Kototoro/ContentCollection.swift:181` 起：观察 `LibraryModel` 和 `ReaderDownloadQueue`。
- 第 184–185 行及 `marked`（第 218 行起）：每次 body 计算均扫描收藏、更新、下载条目，
  构建 Set/Dictionary，再映射全部作品。
- 下载页进度会发布整个 `entries`，虽然作品“已下载”角标通常仅在完成状态变化时才需要更新。
- `LibraryView.swift:219` 起在视图路径中过滤、排序和转换收藏；
  `SourceBrowseView.swift:218,280` 在父视图计算时映射全部条目及身份。
- 历史/更新页按日期构建多个 `ContentCollection`，各集合会重复构建同一份全局角标索引。

影响条件：大作品库、长分页列表、下载进度/作品库状态在滚动期间更新。`LazyVGrid` 仅延迟视图生成，
不会让进入它之前的全量集合处理变成惰性。不能据此声称每一帧滚动都会重算整个列表；
实际更新次数需通过 SwiftUI Instruments 验证。

建议：在数据变化边界生成可复用的角标索引/显示快照，网格只依赖其所需的状态；下载页数变化不应
使“已完成作品集合”失效。筛选排序在对应输入变化时计算，避免为每个子网格维护独立的重复缓存。

### 4. P2：图片任务空闲间隙触发全缓存扫描，并阻止新的图片任务进入

- `iosApp/Kototoro/ReaderStorage.swift:25–44`：最后一个图片租约释放就调用 idle action。
- `ReaderStorageView.swift:51,119–134`：idle action 执行自动清理，进入全局 maintenance。
- `ReaderStorage.swift:206–209`：即便远未达到预算，也先枚举全部缓存文件并按修改时间排序。
- maintenance 期间，`ReaderStorageAccess.enter()` 挂起新请求，直到扫描/清理结束。

影响条件：缓存文件多、请求批次间有空隙；滚动过程中短暂没有图片任务，并不等于用户停止滚动。
该扫描在存储 actor 上执行，**不是已确认的主线程扫描**，主要风险为后续封面出图停顿及 I/O 争用。

建议：自动维护增加合并/节流与明确的空闲调度；未超预算时避免排序，必要时维护近似占用计数，
定期精确校对。保留存储租约，不能绕过并发读取保护。

### 5. P1（来源图标网格冷启动）：视图初始化同步读磁盘缓存

- `iosApp/Kototoro/SourceIcon.swift:18`：`SourceIcon.init` 调用 `SourceIconStore.cached`。
- 第 55 行：`SourceIconStore` 是 `@MainActor`。
- 第 67–70 行：内存未命中时直接 `Data(contentsOf:)` 和 `UIImage(data:)`。
- 第 88–90 行：获取图标后，PNG 编码、目录创建和原子写盘也在主 actor 的任务里。

影响条件：这里是“来源图标网格”，不是作品封面网格。进程重启后快速滑过大量来源时，各图标首次
出现都可能触发同步磁盘读取；已命中内存后这一读取成本消失。`UIImage(data:)` 不保证完成全部
显示解码，不能把它的耗时等同于完整解码耗时。

建议：初始化仅查内存；磁盘读取、图片准备和写入通过后台任务完成，主 actor 只发布结果，保留同键去重。

探针使用合成数据和独立临时目录，未读取或修改用户作品库与缓存。

## 暂不列为已证实瓶颈的项目

- 封面逐张 0.2 秒淡入、圆角/渐变/阴影可能增加合成开销，但没有 GPU / hitch trace 证明其占比。
- 嵌套惰性容器、系统底栏滚动收缩需要实测；不因存在 `LazyVGrid` 就归因于 SwiftUI。
- 扩展调用的同步 JNI 在 Kotlin `Dispatchers.IO` 上运行；封面校验与解码使用 detached task，
  本次没有发现“所有图片都在主线程下载/解码”的依据。
- 图片请求已有同键去重、等待者取消、下载和解码并发门限，且封面已有 64 MiB 解码缓存；
  问题不是完全缺少缓存或并发控制。

## 下一轮根因验收

需要目标设备、具体页面/来源、条目规模和构建类型，在同一 Release 构建下对固定内容做重复上下滑动。
先记录冷缓存、热缓存、下载关闭/开启四种情景，采集 Animation Hitches、SwiftUI 长 body 更新、
Time Profiler、内存峰值及封面解码次数。每次只变更一个因素，保留相同数据和滑动路线。

优先比较：

1. 扩展封面使用目标尺寸后，内存/重复解码/往返滑动 hitch 是否同步下降。
2. 下载关闭后卡顿是否消失；若是，比较队列持久化与角标更新。
3. 来源图标网格首次与再次往返的差异，确认同步磁盘读取占比。
4. 已加载完成的热网格仍卡顿时，检查视图更新、布局和渲染，而不是继续归因网络。

参考 Apple 官方方法：[SwiftUI 性能分析](https://developer.apple.com/documentation/xcode/understanding-and-improving-swiftui-performance)、
[列表与集合视图图片准备](https://developer.apple.com/documentation/uikit/uiimage/building_high-performance_lists_and_collection_views)。
