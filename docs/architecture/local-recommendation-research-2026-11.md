# 本地推荐：重写与研究记录（2026-11）

这份文档记录 2026-11 对本地推荐（推荐页的口味、热门、最新方向）所做的重写，以及围绕它做的评估方法与模型调研。
目的是让后来的人知道：做过什么、测出了什么、哪些结论可靠、哪些方向已经试过并放弃。

> 评估用的脚本和下载的模型留在作者本机的临时目录，没有进仓库；第 7 节写明了复现所需的数据来源和参数。
> 评估只用了作者一份真实书库备份的**汇总统计**，文档里不含任何作品标题、来源标识或个人阅读内容。

## 1. 摘要

1. 本地推荐的管线已经重写：每个来源固定问两个列表，所有候选放在同一个分数尺度上，按来源轮流发牌，
   每个来源的名额随书库里来自它的作品比例变化。不再有随机轮换、过期衰减、方向配额等机制。
2. **"读完 vs 弃读"不能衡量兴趣。** 一部作品被打开本身就是兴趣信号，弃读可能只是先放着。
   本轮早期依据这个指标做的几项取舍（书库频率降权、多兴趣聚类、读完概率乘数）都不应再当作证据，见 §3.1。
3. 在"相似作品检索"上，**标签加类型的内容相似度是基础**；简介向量（GIST）只多一点，封面向量和 Forge2Vec 很弱。
4. 在"书库口味匹配"上，封面向量略占上风，但和标签加类型的差距在误差内，样本只有 59 个正例。
5. **作者书库里的大部分条目是图库类来源的作品，AniList 没有对应条目**（§5），所以所有基于 AniList 的评估只覆盖书库的少数派。
6. 不建议采用：Forge2Vec、EmbeddingGemma 2、用 AniList 补标签。封面画风（MobileCLIP-S0）可以作为以后可选的微调，尚未实现。

## 2. 已落地的重写

代码在 `core-domain` 的 `suggestions/domain`（三端共用）、`core-library` 的 `SourceSuggestions`、Android 的
`SuggestionsWorker` 和推荐设置页。

### 2.1 管线

- **每个来源问两个列表**：一个是读者读过的题材（来源提供的标签里取最匹配的，没有就退成普通热门），一个是最新。
  挑标签时在读者最常读的前 50 个标签里找来源实际提供的那个，而不是只看前 10 个——后者在书库标签很具体时，
  普通来源一个也匹配不上（实测 20 次里 0 次）。
- **收集**：每个来源各自超时，全部等完再汇总，不再用"先到先得取前 480 条"。
- **打分**：所有方向同一个尺度：`(1 + 口味系数 × 标签相似度) / (1 + 名次 / 10)`，再乘质量系数。
  口味方向曾因为用另一个更小的尺度而排在每个来源队列末尾，160 个名额里**一条都选不上**，这是重写时引入的回归，
  已加测试 `every direction the sources answered for is represented`。
- **选取**：按来源轮流发牌，每轮内部按分数排序；社区推荐每 4 条插 1 条；同一批抓取结果得到同一个列表，没有随机。
- **来源名额**：按书库里来自该来源的作品比例：≥8% 每轮 3 个，≥2% 每轮 2 个，有作品但更少 1 个，没有则每两轮 1 个；
  书库少于 20 部时所有来源相同；用户手动选的偏好来源至少 2 个。抓取顺序也按使用量，被截断的是没用过的来源。
  可在设置里关闭。
- **新鲜度**：列表在下一次计划重建前 1 小时内算新鲜，周期任务和重试直接跳过；手动刷新、改推荐设置、追加加载不受限。
- **口味画像**：成人作品和普通作品各建一份口味（只有一种或另一种没有读过的作品时用整体）；
  标签规范化时合并图库站的命名空间前缀（`tag:`、`female:` 等），并把作者、社团、语言、原作、角色这类
  发布元数据排除出口味。

### 2.2 移除的机制

随机轮换与按日期的种子、过期衰减、多来源一致性加成、标签多样性重排（MMR）、方向配额、语言分组上限、
固定的"热门来源"名单（EverythingMoe 快照）、"优先收藏来源"、`SourceBalancedSelector`（死代码）。

### 2.3 设置

按使用情况分配来源份额（可关）、来源使用情况面板（环形图、扩展类型、名额倍数）、更新频率（6/12/24 小时或仅手动，
仅 Android）、隐藏成人内容开关（与来源设置里是同一个设置）。

## 3. 评估方法与教训

### 3.1 "读完 vs 弃读"为什么不对

最早的评估把"读完（进度 ≥ 50%）"当正例、"读几页后放弃（≤ 10%、非收藏、21 天未动）"当负例，算 AUC（0.5 为抛硬币）。
这个指标衡量的是"会不会读完"，不是"感不感兴趣"：

- 不感兴趣的作品根本不会被打开，所以打开过就是正信号；
- 弃读很可能只是先放着，不是不喜欢；
- 口味分在这个指标上接近 0.5 恰恰是预期的，因为两边都是读者感兴趣的作品。

在该指标上测过的结果（**仅供参考，不能作为兴趣的证据**）：

| 打分方式 | AUC |
|---|---|
| 旧的种子标签 | 0.471 |
| 标签份额加稀有度 | 0.494–0.495 |
| 不加稀有度的画像 | 0.512 |
| 按书库出现频率给标签降权 | 0.448（掉 0.045） |
| 笼统题材名单降权 | 0.495（无变化） |
| 多兴趣聚类 | 0.487（掉 0.008） |
| 按来源与标签的"读完概率"学习 | 0.699 |

"读完概率"在这个指标上最高，但它会把读者"先放着"的来源和标签压下去，方向和目标相反，已移除。
书库频率降权和聚类当时因 AUC 下降被删除，这个理由不成立；它们被删除后的行为没有其他证据支持，需要时可以重新评估。

### 3.2 书库口味评估（A）

正例：作者书库里能匹配到 AniList 的 59 部非成人漫画；对照：AniList 人气榜上不在书库里的 640 部。
对每个方法取"和其余正例最相似的 5 个的平均相似度"作分数，5 折交叉，算 AUC。
这是 PU 式评估（对照里可能有读者其实喜欢的），测的是"像不像书库"，不是"会不会喜欢"。

### 3.3 相似作品检索评估（B）

借鉴 MangaBrain 的做法（§4.5）：用 AniList 用户投票的"喜欢 X 就试试 Y"推荐对做真值。
取漫画、非成人、1046 对，去掉有系列关系的（续作、衍生等，推荐引擎本来就不会给出）后剩 1014 对；
候选池是这些作品加人气榜前 2000 部，共 2218 部。指标是目标作品排进前 10、前 50 的比例和 MRR。
随机排的 recall@10 约 0.005。

### 3.4 遇到的坑

- A 组评估代码曾用"池子里任意前 59 部"当作书库去比较，得出低于 0.5 的荒谬 AUC。
  修复后，同批数据上封面和 Forge2Vec 的数字与之前独立测的结果完全吻合，这也验证了流程。
  **结果不合常理（低于抛硬币）时先怀疑评估代码。**
- 正例只有 59 个，估计误差约 ±0.04（折间标准差 0.03–0.12），只能区分"明显有效"和"基本无效"。
- B 的池子只有 2218 部，MangaBrain 的是约 17 万部，**绝对数字不可比**，只看方法之间的相对顺序。
- 评估用的是 AniList 的标签（人工整理、带权重、每部几十个），应用里候选的标签来自各来源，少、无权重、词汇各异，
  所以标签方法的成绩是上限。

## 4. 实验结果

### 4.1 书库口味匹配（A，AUC，近邻数 5）

| 方法 | AUC |
|---|---|
| 封面 MobileCLIP-S0（fp32） | 0.671 ± 0.088 |
| 封面 DINOv2-small | 0.662 ± 0.084 |
| 封面 SigLIP-base（int8） | 0.646 ± 0.066 |
| 封面 EmbeddingGemma 2 视觉（fp32，平均池化） | 0.646 ± 0.102 |
| 标签加类型（0.6/0.4） | 0.608 ± 0.027 |
| MangaBrain 组合（GIST 0.5 / 标签 0.3 / 类型 0.2） | 0.590 ± 0.029 |
| Forge2Vec，标题加简介加类型（加封面 0.565） | 0.560 ± 0.037 |
| Forge2Vec，只用标题和类型 | 0.537 ± 0.042 |
| 标签 | 0.526 ± 0.054 |
| 类型 | 0.487 ± 0.058 |
| GIST 简介向量 | 0.450 ± 0.126（不可靠） |
| 颜色直方图（对照基线） | 0.52 |

封面和"标签加类型"的差距在误差内；封面加到标签上没有明显增益（0.634）。

### 4.2 相似作品检索（B）

| 方法 | recall@10 | recall@50 | MRR |
|---|---|---|---|
| MangaBrain 组合（GIST、标签、类型） | 0.339 | 0.655 | 0.167 |
| 标签加类型 + 封面 MobileCLIP（0.75/0.25） | 0.333 | 0.667 | 0.163 |
| 标签加类型（0.6/0.4） | 0.315 | 0.629 | 0.146 |
| 标签（按排名加权的余弦） | 0.283 | 0.629 | 0.132 |
| GIST 简介向量 | 0.227 | 0.466 | 0.118 |
| 封面 SigLIP | 0.091 | 0.231 | 0.051 |
| Forge2Vec，标题加简介加类型 | 0.080 | 0.225 | 0.039 |
| Forge2Vec，只用标题和类型 | 0.075 | 0.231 | 0.036 |
| 类型（Jaccard） | 0.061 | 0.242 | 0.032 |
| 封面 MobileCLIP-S0 | 0.055 | 0.167 | 0.032 |
| 封面 DINOv2-small | 0.038 | 0.097 | 0.017 |

recall@10 的 95% 误差约 ±0.03：简介向量加进标签（0.315 到 0.339）和封面加进标签（到 0.333）都**不显著**。

### 4.3 封面编码器的成本与量化

| 编码器 | 体积 | 单张耗时（Apple 芯片 CPU） |
|---|---|---|
| MobileCLIP-S0 | 45 MB（量化版 12 MB） | 50 ms |
| DINOv2-small | 88 MB | 57 ms |
| SigLIP-base（int8） | 约 99 MB | 145 ms |
| EmbeddingGemma 2 视觉 | 670 MB（fp32），195 MB（int8） | 1045 ms |

- MobileCLIP-S0 的 `vision_model_int8` 含 `ConvInteger` 算子，onnxruntime 1.19.2 的 CPU 上没有实现，加载失败；
  应用里是 1.24.3，**是否支持未验证**，要在 Android 上实测。
- 同体积的 `vision_model_quantized`（uint8）能加载，AUC 0.654（fp32 为 0.671，在误差内），
  在这颗芯片上反而更慢（81 ms），手机 ARM 上要另测。
- EmbeddingGemma 2 的 int8 版用了 `GatherBlockQuantized`，同样加载失败，改用 fp32 版评估；
  预处理经"同图缩小 15% 相似度 0.989、不同图 0.555"自检确认正确，三种池化里平均池化最好（事先定为主结果）。
  效果和三个小模型没有区别，却慢约 20 倍、大一个数量级。

### 4.4 Forge2Vec（`Lorg0n/hikka-forge2vec`）

- 输入标题、简介、类型、年份、评分，封面可选且权重最多 10%；输出 256 维；Apache-2.0。
  权重 852 MB（含 SigLIP2 视觉塔与多语言 MiniLM 文本塔），PyTorch 格式，要 Python ≥ 3.10，没有 ONNX，
  分词用 17 MB 的词表，三端都要自己实现。
- 训练数据是作者私有的 hikka.io 目录加合成数据，只有定性评估，下载量很少。
- 在 §4.1、§4.2 里都很弱，不建议采用。候选列表通常没有简介，只给标题和类型时更弱。

### 4.5 MangaBrain（`Breezyslasher/MangaBrain`）

- 自托管的内容推荐服务：Python、Postgres、pgvector，带 Android 和 iOS 客户端；没有开源协议，**只能借鉴思路**。
- 目录取自 AniList（约 2 万部动画、15 万部漫画类）；用 `avsolatorio/GIST-Embedding-v0`（768 维）对类型、前 15 个标签、
  简介编码（有简介时不放标题，避免子词泄漏）；打分 `0.5 × 简介余弦 + 0.3 × 标签余弦 + 0.2 × 类型 Jaccard`，
  类型缺失时把权重分给其他项，不当作 0；多种子推荐把向量和标签取平均；"为你推荐"按用户自己评分的百分位加权抽样。
- 原则：**打分里绝不读取人气**，有测试保证。
- **评测方法值得借鉴**：AniList 投票推荐对做真值，只用于评估；它报告 GIST 768 维 r@10 为 0.174（池子是全目录）。
- 它自己的文档记录 Jikan 公共接口已在 2026-10-01 停用。

## 5. 书库构成与 AniList 覆盖

一个与直觉不符的发现：用标题去 AniList 匹配，最早只匹配到约 8%。起初我以为是中文译名搜不到，实测后不是：

- 抽样 300 部"非成人"漫画：中文标题只有 20 部（约 7%）。
- 四种匹配规则（只看第 1 个结果 / 看前 5 个 / 加上作品的其他名字 / 再合并简繁体）的匹配率都在 10% 左右，没有差别。
- **86.7% 的作品，AniList 对它们的任何名字都没有返回候选。**
- 这些作品的标题 63% 以方括号开头（"[社团/作者] 标题"），另有一批带活动、Digital、Raw 标记，中位数长度 63 个字符
  （匹配上的是 16）；大部分来自同一个图库类来源。它们是同人志或图库条目，不是 AniList 收录的系列作品。
- 因此 §4 的两组评估只覆盖书库里的商业漫画那部分（约十分之一）；"标签只有 4%–8% 能映射到规范标签"也是同一个原因，
  图库站有自己的标签体系，规范标签是为商业漫画设计的。
- 这些条目在应用里被判成"非成人"，来源或作品的成人标记可能没有设对，会影响"成人和普通口味分开"的效果。

## 6. 决定与未决

| 方向 | 结论 |
|---|---|
| 以标签加类型为核心 | 采用（已是现状），提升标签质量比换模型更值 |
| 简介向量（GIST） | 暂不做：增益不显著，要简介，要 440 MB 模型 |
| Forge2Vec | 不做 |
| EmbeddingGemma 2 | 不做：没有收益，慢 20 倍 |
| AniList 补标签 | 不做：只覆盖约十分之一 |
| 读完概率、书库频率降权、多兴趣聚类 | 已移除；依据的指标不衡量兴趣，必要时可重新评估 |
| 封面画风（MobileCLIP-S0） | 未做；效果与标签相当，可作为以后的可选微调 |

未决事项：

1. **在作者自己的书库上评估**：用图库类来源内部的数据，对比"打开过的"和"同来源的其他作品"。
   需要在应用里拉来源列表，不能离线做。可以先加一个只读调试输出：每个来源抓到几条、被书库标签命中几条。
2. **封面画风**：先在 Android 上验证 MobileCLIP-S0 的 int8 能否加载，再扩大正例到几百个才能比较模型。
3. **图库类来源的成人标记**是否设对。
4. 推荐页的几处改动（口味方向、使用情况面板、封面缓存）还没有在设备上做过完整验证。

## 7. 复现

数据都来自公开接口，没有上传书库内容：

- **AniList GraphQL**（`https://graphql.anilist.co`，限速约 90 次每分钟）：
  推荐对用 `recommendations(sort: RATING_DESC)` 翻页，上限 5000 行；元数据用 `id_in` 每批 50 个，
  取标题、简介、类型、标签（带排名）、封面地址、关联关系；人气榜用 `sort: POPULARITY_DESC`。
- **模型**（Hugging Face）：`Xenova/mobileclip_s0`、`Xenova/dinov2-small`、`Xenova/siglip-base-patch16-224`
  （ONNX 版，预处理分别为：MobileCLIP 缩短边 256 后居中裁剪、不归一化；SigLIP 直接缩放 224、均值方差 0.5；
  DINOv2 缩短边 256 后居中裁剪 224、ImageNet 均值方差）、`onnx-community/embeddinggemma-2-ONNX`、
  `Lorg0n/hikka-forge2vec`、`avsolatorio/GIST-Embedding-v0`。
- **评估**：A 用 5 折，相似度取与其余正例最相似的 5 个的平均；B 对每对计算目标在池中的名次，
  池里排除种子自己和与它有关联的作品。Forge2Vec 和 GIST 需要 Python ≥ 3.10 的独立环境（`uv venv --python 3.11`）。
- 提示：AniList 的 `description` 要先去掉 HTML；GIST 的文本配方见 §4.5。
